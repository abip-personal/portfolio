## Context

Agriluso ([agriluso.pt](https://agriluso.pt)) connects Portuguese farmers with agronomists in real time. A farmer with a problem in a field — a pest, a disease, a question about a treatment window — should be able to reach a qualified agronomist, share what they are looking at, and get an answer that is recorded properly.

The "recorded properly" part is the interesting half. Portuguese farmers are legally required to keep a field logbook of treatments applied. It is paperwork nobody wants to do and everybody has to, and it is generated as a by-product of exactly the conversations the platform already hosts.

I am the lead developer on it — I architected the platform and drive most of the build — with a small team working alongside me. It is in active development and pre-launch.

## Constraints

- **The users are not technical, and they are outdoors.** The mobile app has to work with intermittent or absent connectivity and it has to survive being used with one hand in a field.
- **Geography is a first-class part of the data model.** Parcels, treatments and advice are all located. This is not a lat/long column bolted onto a table.
- **Personal data, and a legal record.** GDPR applies, and the logbook is a compliance artefact, so its integrity matters more than most application data.
- **A small team.** Every service I add is a service one of us has to operate. That is the dominant constraint on the whole design.

## Architecture

Three services, chosen because they have genuinely different runtime shapes, not because microservices are fashionable.

The **REST API** (NestJS, TypeORM, PostgreSQL with PostGIS) owns the domain: users, parcels, crops, treatments, the logbook. PostGIS rather than application-level geo maths, because parcel geometry, containment and proximity queries belong in the database where they can be indexed.

The **real-time chat service** (Socket.io, Redis) handles the conversation between farmer and agronomist. Redis carries pub/sub across instances and session state. On top of the message stream sits an NLP layer that recognises actionable intent in what people are already typing — a mentioned treatment, a product, a date — and surfaces it as a smart action rather than asking the user to fill in a form.

The **ingestion service** pulls weather and phytosanitary data on a schedule and normalises it into the same geographic model, so advice can be contextualised by what is actually happening in that area.

The **mobile app** is React Native and Expo, built offline-resilient: local writes queue and reconcile when connectivity returns.

## Key decisions

**PostGIS instead of geo in the application layer.** The alternative — store coordinates, do containment and distance in Node — is simpler to start and needs no extension. It loses as soon as you want "which parcels are within this alert zone" to be fast and correct across polygon geometry rather than points. Doing that in application code means reimplementing spatial indexing badly.

**A separate chat service rather than websockets in the monolith.** Keeping it in the API would be one fewer thing to deploy, which matters a lot when you are a small team. It loses because the connection-heavy, long-lived, memory-resident workload scales along a completely different axis from the request/response API. Coupling them means scaling the API for chat connections, or degrading chat when the API is under load.

**Offline-first in the mobile app, not offline-tolerant.** Treating connectivity as normal and offline as an error state is far less code. It loses because the actual usage location is a field. If the app is only usable back at the house, the logbook gets filled in from memory later, which is exactly the failure mode the product exists to remove.

**Extract structure from conversation rather than ask for it in a form.** A form is unambiguous and trivial to build. It loses on adoption: a farmer mid-problem will describe the problem, not complete a treatment record. Making the smart action a confirmation step over extracted data puts the compliance work where the user already is.

**GDPR handling built in from the first migration.** Consent, export and erasure designed in rather than added later. The cost is real up front. Retrofitting erasure across a schema with denormalised personal data is a rewrite, and I have watched that happen elsewhere.

## Results

The platform is pre-launch, so the honest result statement is about what exists and works, not about traction:

- Three services running under Docker with AWS as the deployment target.
- A REST API over PostgreSQL/PostGIS covering the full domain model, with GDPR-by-design consent, export and erasure.
- A real-time chat service with NLP-driven smart actions feeding structured records.
- A React Native/Expo mobile app that functions without connectivity.
- Automatic generation of the legally required digital field logbook as a by-product of normal use.
